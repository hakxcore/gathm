connected phone. No branches were merged and no model settings were changed.

## Measured improvement

| Measurement | Before | After | Samples |
| --- | ---: | ---: | --- |
| Bash tool metadata listing | 5.427 s | 0.094 s | Median of 5 per version, alternating order |
| Full `gathm list --json` | 6.924 s | 0.946 s | 1 baseline, median of 3 after |

The metadata operation is **57.7× faster**, a **98.3% reduction in elapsed time**.
The full command improved by approximately **7.3×** in this small sample.
Every comparison produced byte-for-byte identical output for all 55 shell tools.
These are catalog measurements, not AI chat speedups.

`lib/schema.bash` previously launched `grep`, `sed`, and two `tr` processes for
*each field* of every manifest, plus `basename` and command substitutions. The
new list reader parses each manifest once using Bash built-ins. Individual
field lookups also avoid external pipelines. Existing scalar interpretation,
field defaults, ordering, and filtering are retained.

The isolated comparison used a temporary directory containing the candidate
library and a symlink to the phone's actual tools directory. No tool was run.
After that comparison passed, the actual phone file was backed up and replaced.
The full launcher command and regression suite were then checked on the phone.

## Remaining latency

| Baseline measurement | Observed |
| --- | --- |
| `gathm --version`, on phone | 0.182 s median, 3 runs |
| Fresh Pilot process import | 16.870 s first run; 4.422 and 4.304 s afterward |
| Direct model, “Reply with exactly: Ready.” | 7.684 s first observed request; 1.736 and 1.742 s afterward |
| Gathm API, “hello” | 20.144, 21.023, and 15.412 s |

The model and API measurements used USB-forwarded HTTP and include transport
overhead. Their prompts and output lengths differ, so their difference must
**not** be reported as framework overhead. The first observed request is not a
controlled cold boot: the model server was already running, and Android page
cache and scheduling state were not reset.

The API starts `pilot/chat_once.py` in a new Python process for every message.
The measured 4.3–4.4 s warm import cost therefore remains an optimization target;
a reusable worker would need timeout, crash recovery, configuration refresh,
and conversation-isolation tests. No such API lifecycle change was made here.
The metadata patch does not alter the Python tool catalog used by chat.

An exploratory prompt comparison was also run against another branch, but the
server reused prompts from earlier sessions. Those numbers are excluded from
speedup claims. The saved benchmark's `--prompt-cache` mode now uses a unique
prefix and sample markers to distinguish prefix reuse from exact prompt replay.
That revised mode was not used to produce the measurements above.

The newer `8031225` loop-guard branch passed its 15 Pilot regression tests and
23 routing-harness checks in an isolated Mac copy. Its connectivity test had
2 failing local-server assertions on the Mac; the cause was not investigated.
That branch was not merged or installed, and its live-chat behavior is unverified.
